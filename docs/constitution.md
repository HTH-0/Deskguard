# 프로젝트 원칙

이 문서는 개발 중에 바뀌지 않는 규칙을 모아 둔다. 명세서, 설계서, 테스트가 이 문서와 충돌하면 이 문서를 기준으로 판단한다. 원칙을 바꿔야 할 때는 먼저 [DECISIONS.md](../DECISIONS.md)에 변경 이유를 기록한 뒤에 이 문서를 고친다.

상태: 초안 (사용자 검토 전)

## 1. 범위

1. 이번 범위는 입력 방어로 한정한다. 출력(응답) 필터링은 확장 범위이며 구현하지 않는다.
2. 막는 대상은 두 가지이다. 첫째는 일반 인젝션으로, 지시 무시 유도, 역할극 탈옥, 시스템 프롬프트 탈취, 권한 사칭이다. 둘째는 [도메인 정책서](domain-policy.md)에 정의한 사내 HR 헬프데스크의 금지 항목(F1~F4)이다. 금지 항목은 3~5개로 제한한다.
3. 금지 콘텐츠 요청(`disallowed_content`)과 편향 발언 강요(`bias_injection`) 유형은 이번 범위의 방어 대상에서 보류하고, 외부 서비스로 전송하지 않는다. 데이터셋에서 삭제하지는 않는다. (근거: [DECISIONS.md](../DECISIONS.md) 2026-10-26 도메인 정책 항목)
4. 챗봇은 개인 데이터를 조회하지 않고 규정과 절차를 안내하는 데 한정한다. 프롬프트에서 주장하는 신원은 신뢰하지 않는다.
5. 프론트 화면은 평가 대상이 아니다. 마지막에 만들고 완성도에 시간을 쓰지 않는다.

## 2. 측정 무결성

1. `dataset.csv`의 `split=design` 데이터는 룰 설계와 단위 테스트 픽스처에만 쓴다.
2. `split=eval` 데이터는 6단계 측정 전까지 열어보지 않는다. 테스트, 룰 설계, 판정 프롬프트 튜닝 어디에도 쓰지 않는다.
3. design 데이터 기반 룰 회귀 테스트는 룰이 의도대로 동작하는지 확인하는 용도이다. 탐지율 주장의 근거로 쓰지 않는다.
4. 탐지율과 오탐율은 eval 데이터로만 측정하고, 유형(`type`)별과 언어(`lang`)별로 나누어 기록한다.
5. 정답 라벨은 사람이 분류한 `dataset.csv`의 `label`이다. 판정 모델이 라벨을 정하지 않는다.

## 3. 판정 모델의 위치

1. 처리 순서는 패턴 필터(1차)가 먼저이고 판정 모델(2차)이 나중이다. 패턴 필터는 차단만 하며, 룰이 차단하지 않은 프롬프트는 모두 판정 모델이 보완 판단한다. (근거: [DECISIONS.md](../DECISIONS.md) 2026-10-26 항목)
2. 판정 모델은 운영 중에 들어오는 새로운 입력을 판단하는 구성요소이다. `dataset.csv`는 이를 검증하는 정답지이다.
3. 판정 모델은 시스템의 일부이며 검증 대상이다. 채점자로 쓰지 않는다.
4. 판정 모델은 확률적으로 동작한다고 전제한다. 판정 결과의 정확성을 단위 테스트의 단정으로 보장하지 않는다.
5. 판정 모델의 한계(judge injection, 응답 모델과 같은 약점)는 숨기지 않고 분석 문서에 기록한다.

## 4. 비밀과 외부 호출

1. API 키를 소스, 설정 파일, 테스트, 로그에 적지 않는다. 환경변수로만 주입한다.
2. 자동 테스트는 실제 Gemini API를 호출하지 않는다. 가짜 응답으로 대체한다.
3. 실제 API를 호출하는 확인은 기본 테스트에서 제외하고, 직접 실행하는 스모크 확인으로 분리한다.

## 5. 개발 순서

1. 명세 → 테스트 → 코드 순서로 진행한다.
2. 명세와 코드가 어긋나면 코드를 먼저 고치지 않고 명세를 먼저 고친다.
3. 결과가 결정적인 코드(룰 매칭, 필터 체인, 응답 파싱, 예외 처리)는 TDD로 만든다.
4. 확률적인 품질(판정 모델의 탐지율)은 테스트가 아니라 평가로 검증한다.
5. 테스트 없이 동작을 추가하지 않는다. 기존 코드는 변경 전에 현재 동작을 테스트로 고정한다.

## 6. 사람이 판단하는 부분

아래 항목은 AI에게 통째로 맡기지 않는다. AI의 도움을 받더라도 최종 결정은 사용자가 내린다.

1. 데이터 분류와 라벨
2. 룰 패턴 선정
3. 판정 기준과 판정 프롬프트의 수정 방향
4. 측정 수치의 해석
5. 뚫린 케이스의 원인 분석과 개선 방향
6. 명세서의 미결 항목에 대한 결정

## 7. 기록과 이해

1. 결정이 생기는 시점에 [DECISIONS.md](../DECISIONS.md)에 후보, 선택, 이유를 남긴다.
2. 못 막은 공격은 숨기지 않고 원인과 함께 기록한다.
3. 각 단계가 끝날 때, 요청이 들어와서 응답이 나갈 때까지의 흐름을 사용자가 자기 말로 설명할 수 있어야 완료로 인정한다.
4. 라이브러리와 프레임워크 버전처럼 계속 바뀌는 사실은 추측하지 않고 직접 확인한다.
