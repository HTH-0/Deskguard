# 업무 요청 틀 생성 지시문 (5일차 평가 세트용)

주제 재정의 이후의 새 지시문이다. 옛 HR용 지시문은 [generation_prompt.md](generation_prompt.md)이며 쓰지 않는다. 명세 AC-10.1을 따른다.

## 사용 순서

1. 아래 "지시문"을 생성기 3종에 각각 새 대화로 붙여 넣는다: ChatGPT, 이 프로젝트와 무관한 Claude 새 대화, Gemini. 프로젝트 문서와 이 저장소의 어떤 파일도 같이 넣지 않는다(서로 다른 문체를 얻기 위해서이다).
2. 각 생성기에서 받은 결과를 JSONL 그대로 `docs/eval/templates/chatgpt.jsonl`, `claude.jsonl`, `gemini.jsonl`로 저장한다. 설명 문장이 섞여 있으면 JSONL 줄만 남긴다.
3. 결과를 받은 뒤 사람이 읽고 고치지 않는다. 형식이 틀린 줄만 도구가 거부한다. 틀을 고르거나 다듬으면 측정 결과가 한쪽으로 치우친다.
4. 한 번에 다 나오지 않으면 "이어서 계속"만 보내고, 다른 지시를 덧붙이지 않는다.

## 지시문 (아래 상자 안을 그대로 붙여 넣는다)

```
당신은 회사 직원이 외부 생성형 AI(ChatGPT 같은 서비스)에 보내는 업무 요청 문장의 "틀"을 만든다. 틀 안의 민감한 값은 자리 표시자로 두고, 실제 값은 나중에 프로그램이 가짜로 채운다. 실제 개인정보, 실제 비밀번호, 실제 키는 절대 쓰지 않는다. 틀에는 중괄호 자리 표시자만 쓴다.

[회사 배경]
가상의 물류 SaaS 회사(직원 약 150명)이다. 개발자는 코드와 설정 파일을, 영업과 고객지원은 고객 명단과 메일을, 인사와 재무는 직원 정보와 문서를 외부 AI에 붙여 넣어 일을 시킨다. 말투는 실제 직원처럼 다양하게 쓴다(존댓말, 반말, 메신저체, 짧은 명령형, 긴 설명형, 영어 섞임). 업무 종류도 섞는다(요약, 번역, 표 정리, 메일 초안, 오류 분석, 코드 리뷰, 양식 채우기, 회의록 정리, 보고서 문장 다듬기).

[쓸 수 있는 자리 표시자]
{NAME} 사람 이름
{RRN} 주민등록번호
{FRN} 외국인등록번호
{CARD} 신용카드 번호
{PHONE} 휴대전화 번호
{BANK} 은행 이름
{ACCOUNT} 계좌 번호(은행 이름은 {BANK}로 따로 쓴다)
{EMAIL} 이메일 주소
{PRIVATE_KEY} 개인 키 블록(여러 줄이어도 하나의 자리 표시자이다)
{CONN_STRING} 데이터베이스 접속 문자열
{API_KEY} API 키
{JWT} 로그인 토큰
{PASSWORD} 비밀번호
{CODENAME} 미공개 프로젝트 코드명
{CLIENT} 고객사 이름
{CLASSIFIED} 보안 등급 표시(대외비, Confidential 같은 문구)
{PHONE_LIST} 휴대전화 번호 여러 개의 목록(20개 이상으로 프로그램이 채운다)
{EMAIL_LIST} 이메일 주소 여러 개의 목록(20개 이상으로 프로그램이 채운다)
{HQ_PHONE} 회사 대표 전화(공개 정보이다)
{HQ_EMAIL} 회사 대표 이메일(공개 정보이다)

[만들 틀의 개수와 종류]
1) 민감 항목 틀: 위 항목 중 {NAME}, {BANK}, {PHONE_LIST}, {EMAIL_LIST}, {HQ_PHONE}, {HQ_EMAIL}을 뺀 14개 항목({RRN}, {FRN}, {CARD}, {PHONE}, {ACCOUNT}, {EMAIL}, {PRIVATE_KEY}, {CONN_STRING}, {API_KEY}, {JWT}, {PASSWORD}, {CODENAME}, {CLIENT}, {CLASSIFIED})마다 10개씩, 모두 140개. 틀 하나에는 그 항목의 자리 표시자가 반드시 들어간다. {NAME}, {BANK} 같은 보조 자리 표시자는 자연스러울 때만 함께 쓴다.
2) 여러 항목 틀 15개: 한 문장에 서로 다른 항목 2~4개가 들어간다.
3) 대량 틀 10개: {PHONE_LIST} 또는 {EMAIL_LIST}가 들어간다(각 5개).
4) 정상 틀 35개: 민감한 값이 전혀 없는 평범한 업무 요청이다. 어떤 자리 표시자도 쓰지 않는다. 숫자, 날짜, 부서 이름, 일반 용어, 코드 조각(비밀 값 없음)은 써도 된다. 일부는 민감한 값처럼 보이기 쉬운 평범한 문장이어야 한다(예: 버전 번호, 주문 번호, 회의실 번호, 오류 코드, {HQ_PHONE}이나 {HQ_EMAIL} 안내).

[규칙]
- 틀마다 20자 이상 400자 이하이다.
- 값을 설명하는 문구를 앞에 붙여 쉽게 만들지 않는다(예: "전화번호는"을 항상 붙이는 식의 반복 금지). 값이 문장 중간, 끝, 괄호 안, 표 안, 코드 블록 안 등 여러 위치에 오게 한다.
- 같은 틀을 문구만 바꿔 되풀이하지 않는다.
- 민감 틀에서 "이것은 민감한 정보이다" 같은 사실을 문장에 직접 적지 않는다. 직원은 그렇게 말하지 않는다.

[출력 형식]
JSON Lines이다. 한 줄에 JSON 한 건만 쓰고, 설명 문장과 코드 블록 표시는 쓰지 않는다.
{"kind":"sensitive","items":["PHONE"],"template":"..."}
- kind는 sensitive 또는 normal이다. 대량 틀도 sensitive이다.
- items는 틀에 쓴 민감 자리 표시자의 영문 항목 이름 목록이다(NAME, BANK, HQ_PHONE, HQ_EMAIL은 넣지 않는다). 정상 틀은 빈 목록 []이다.
- 가장 먼저 민감 항목 틀 140개, 다음으로 여러 항목 틀, 대량 틀, 정상 틀 순서로 낸다. 한 번에 다 못 내면 내가 "이어서 계속"이라고 하면 이어서 낸다.
```

## 이 문서를 만든 이유와 한계

- 틀과 값을 나누면 정답 위치를 코드가 정확히 계산할 수 있다(AC-10.1).
- 3종 생성기를 쓰는 이유는 한 모델의 문체에 치우치지 않기 위해서이다. 그래도 합성 문장이라는 한계가 남으며 보고서에 적는다(AC-10.6).
- `{PRIVATE_KEY}`를 만드는 코드는 아직 `fake_values.py`에 없다. 평가 세트 생성기를 만들 때 추가한다.
