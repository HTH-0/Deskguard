# 열린 위험 목록

아직 해소되지 않은 위험을 모아 둔다. 매 단계 보고 때 이 목록의 상태를 함께 확인한다. 위험이 해소되면 상태를 바꾸고, 근거를 [DECISIONS.md](../DECISIONS.md)에 남긴다.

상태 값: 열림 / 확인 중 / 해소 / 수용

공식 문서 확인일: 2026-10-26 (docs.typesafe.ai). 외부 AI의 답변은 근거로 쓰지 않고, 공식 문서에서 직접 확인한 내용만 해소 근거로 삼는다.

## R1. Java에서 Jev를 호출할 수 있는가

- 상태: 해소 (2026-10-26 실제 호출로 검증)
- 호출 검증 결과: Windows PowerShell에서 `Invoke-RestMethod`로 `jev-1.14.0`을 3회 호출해 모두 성공했다. 응답은 `model`, `answers.is_attack.noul`(0~1), `usage`(입력 약 300토큰, 출력 21토큰) 구조였다. 한글 문장을 UTF-8 바이트로 전송했을 때 정상 처리되었다.
- 참고: 짧은 문장에도 입력 토큰이 약 300개로 집계되었다. 질문 문구와 고정 구성이 포함된 값으로 보이며, 비용 추정은 이 값을 기준으로 한다.
- 공식 문서 확인 결과:
  - 엔드포인트는 `POST https://api.typesafe.ai/v1/systemone`이다.
  - 인증은 `Authorization: Bearer <API_KEY>` 헤더이고, 본문은 `Content-Type: application/json`이다.
  - 요청 본문은 `model`, `state`(문자열 또는 객체), `questions`(질문 ID를 키로 하는 객체)로 구성된다. Noul 질문은 `type: "noul"`과 `instructions`를 쓴다.
  - 응답은 `model`, `answers`(질문 ID별 값), `usage`로 구성된다. Noul 답변은 0~1 사이 값이다.
  - cURL 예시와 OpenAPI 스펙(`https://api.typesafe.ai/openapi.json`)이 제공된다. 따라서 Python 중계 없이 Spring Boot의 `RestTemplate`로 호출할 수 있을 것으로 판단한다.
- 남은 확인: 실제 키로 호출 1건을 보내 응답 구조를 확인한다. 오류 응답의 JSON 필드 구조는 문서에 없으므로 호출로 확인한다.
- 외부 답변과 다른 점: 외부 답변이 언급한 `/v1/decisions` 경로와 게이트웨이 파트너 목록은 공식 문서에서 확인하지 못했다.
- 확인 시점: 스텝 2.5

## R2. 한국어 판정 정확도

- 상태: 완화 (2026-10-26 PoC 합격 기준 전부 충족. 6단계에서 언어별 측정 후 재판단)
- 공식 문서 확인 결과: 영어가 주 학습 언어이고 정확도가 가장 높다. CJK 등 다른 언어는 처리되지만 같은 수준의 정확도는 보장되지 않으며, 비영어 작업 전에 직접 테스트하라고 권장한다. 또한 지시와 기준은 같은 언어로 맞추라고 권장한다.
- 배경: `dataset.csv`는 ko 153건, en 363건, de 42건이다.
- 확인 방법: `split=design`의 한국어 문장 소규모 샘플로 사전 검증(PoC)을 한다. 합격 기준은 결과를 보기 전에 먼저 정한다. 질문의 `instructions` 언어(한국어/영어)에 따른 차이도 함께 본다.
- 대응 후보: 한국어 패턴 필터 비중 상향, 애매한 구간의 일반 LLM 병행(폴백)
- PoC 결과 (2026-10-26, 한국어 질문 문구 K, 임계값 0.5): 일반 인젝션 24/24 탐지, 도메인 위반 36/40 탐지, 도메인 정상 오탐 1/80, 일반 정상 오탐 2/40. 합격 기준 C1~C6을 모두 충족했다. 다만 표본이 작고 질문의 참/거짓 기준을 이 문장들의 경계를 알고 쓴 것이라 낙관적일 수 있으므로 성능 주장으로 쓰지 않는다. 약점으로 관찰된 것은 "해도 될까요?", "열어줄 수 있나요?" 같은 가능 여부·허락을 묻는 형태의 공격(의문형 공격 10문장 중 3문장 놓침. 그중 둘은 라벨 자체가 애매하며, 상세와 개선안은 [design.md](archive/design-v1-hr.md) 4절)과, 업무 지시 안의 "무시하고"(예: 회의록은 무시하고 이메일만 요약)를 인젝션으로 오판하는 경우이다.
- 확인 시점: 스텝 2.5 (사전 검증), 6단계 (언어별 측정)

## R3. Early Access 단계의 변경 가능성

- 상태: 수용 (완화책 적용)
- 배경: API, 가격, 성능이 바뀔 수 있다. 폐기(deprecation) 정책은 문서에 없다.
- 완화책: 판정 호출을 `Judge` 인터페이스 뒤에 두어 다른 모델로 교체할 수 있게 한다.
- MCA 원문 확인 (2026-10-28, 수정일 2026-09-23): Early Access나 베타 전용 조항은 없다. 대신 2.5(API 업데이트로 비호환이 생길 수 있고, 통지는 "상업적으로 합리적인 노력"), 9.3("AS IS"), 16.7(약관 변경은 통지 60일 후 효력)이 있다.
- 확인 시점: 스텝 5 (설계서)

## R4. 확률 값의 신뢰도 (보정)

- 상태: 열림
- 배경: 공식 가드레일 쿡북은 샘플 15개로 시연했고 정확도, 재현율, 오탐율 같은 정량 지표를 제시하지 않는다. 임계값은 자체 라벨링된 데이터로 정해야 한다고 읽힌다.
- 확인 방법: 6단계에서 확률 구간별 실제 적중률과 임계값별 탐지율/오탐율을 측정한다.
- 확인 시점: 6단계

## R5. 외부 서비스로 데이터를 보내는 문제

- 상태: 수용 (2026-10-26 사용자 승인, 범위: 실제 사용자가 없는 포트폴리오 단계)
- 공식 문서 확인 결과:
  - 개인정보 처리방침에 "사용자 데이터로 모델을 학습시키지 않겠다"는 약속이 포함된다고 적혀 있다. 모델 문서에는 "고객 요청과 응답으로는 Jev를 학습하지 않으며 계정별 파인튜닝은 없다"고 적혀 있다.
  - 데이터 보관 기간, 제3자 제공, 데이터 위치는 문서에 없다. 보관은 DPA(Data Processing Agreement)에 포함된다고만 적혀 있다.
  - 제로 데이터 보관(ZDR)은 엔터프라이즈 고객에게 제공된다.
- 외부 답변과 다른 점: 외부 답변이 인용한 영문 문구와 "제3자 제공 제약" 내용은 공식 문서에서 같은 표현으로 확인하지 못했다.
- 약관 전문 확인 결과 (2026-10-26, Privacy Policy, DPA, MCA):
  - 학습 사용: Privacy Policy 원문이 "We will not train or fine tune any artificial intelligence or machine learning models on your prompts or other Input."이라고 명시한다. MCA 4.1도 고객의 사전 동의 없이 고객 데이터를 학습 데이터셋에 포함할 수 없다고 한다. (앞서 외부 답변이 인용한 문구와 유사하며 공식 원문으로 확인됨)
  - 보관 기간: 입력 데이터의 구체적 보관 기간은 문서에 없다. 개인정보는 "서비스 제공에 합리적으로 필요한 기간", DPA는 "처리 목적을 고려해 필요한 기간"이라고만 한다. API 요청 로그 보관 여부도 문서에 없다.
  - 데이터 위치: 서비스는 미국에서 호스팅된다. 한국에서 전송하면 국외 이전에 해당한다.
  - 제3자: 계열사, 서비스 제공 벤더, Google Analytics, 결제 처리업체에 제공될 수 있다. 하위 처리자 목록은 Trust Center 페이지를 참조하라고 하는데 내용을 확인하지 못했다.
  - 남용 모니터링: 사기·남용 방지 목적으로 데이터를 처리할 수 있다(MCA 4.1). 운영자가 입력을 열람하는지는 문서에 없다.
  - 유해 입력 조항: Privacy Policy에 "객체적으로 문제가 되는 콘텐츠를 입력하면 개인정보가 공개될 수 있다"는 조항이 있다. R8과 연결된다.
- 수용 조건 제안: 이 프로젝트는 실제 사용자가 없는 포트폴리오이며 전송 데이터가 공개 데이터셋과 직접 작성한 문장이다. 이 범위에서는 보관 기간 불명과 미국 호스팅을 수용한다. 실제 사용자 입력을 받는 서비스로 확장하면 개인정보 마스킹과 보관 정책을 다시 검토한다.
- 확인 시점: 스텝 2.5 (사용자의 수용 판단)

## R6. 판정 모델 자체가 속는 문제 (judge injection)

- 상태: 열림 (공식 문서가 약점으로 인정)
- 공식 문서 확인 결과: 모델은 `state`를 기본적으로 적대적인 입력으로 취급하지 않는다. 주입된 지시, 의도적으로 잘못된 틀, 자신의 분류를 주장하는 텍스트가 답을 바꿀 수 있다고 명시한다. 향후 개선 예정이며, 많은 사용자에게 배포하기 전에 충분히 테스트하라고 권장한다.
- 영향: 이 프로젝트의 판정 대상이 바로 적대적 입력이므로 핵심 위험이다. 앞서 "State와 Question 분리로 구조적으로 유리할 수 있다"고 한 가설은 공식 문서로는 지지되지 않으므로 낮춰서 본다.
- 확인 방법: 7단계에서 judge injection 시험 세트를 만들어 측정한다. 질문의 `criteria`에 적대적 패턴을 명시하는 방안을 시험한다.
- 확인 시점: 스텝 2.5 (맛보기), 7단계

## R7. 모델 별칭 이동과 결과 재현성

- 상태: 열림 (완화책 확정 예정)
- 공식 문서 확인 결과: `jev-latest`는 새 릴리스가 나오면 이동하므로 코드를 바꾸지 않아도 답이 달라질 수 있다. 특정 버전에 맞춰 임계값을 조정했다면 버전 ID(예: `jev-1.14.0`)를 직접 보내라고 권장한다. 응답의 `model` 필드에 실제 버전이 표시된다.
- 완화책(제안): 설정 파일에 버전 ID를 고정하고, 응답의 `model` 값을 로그와 측정 결과에 함께 기록한다.
- 확인 시점: 스텝 5 (설계서), 6단계

## R8. 허용 사용 정책(AUP) 위반으로 인한 계정 정지

- 상태: 수용 후 진행 (2026-10-28 사용자 결정). 2026-10-27 support@typesafe.ai로 문의했고, 2026-10-28 답장이 왔다. 답장 요지는 "개별 사용 사례를 검토하거나 승인할 법적 여력이 없으니 AUP와 MCA를 참조하라"이다. 사전 승인은 받을 수 없고, 정지 가능성이 남은 채로 진행한다.
- 원문 교차검증 (2026-10-28, AUP와 MCA 모두 수정일 2026-09-23, `curl`로 원문 조회): 외부 LLM의 조언이 인용한 AUP 1.5, 3.4, 3.7은 원문과 일치했다. 그러나 "안전하다, 추가 조치가 필요 없다"는 결론은 과했다. 조언이 다루지 않은 조항은 다음과 같다.
  1. AUP 4절: 위반했거나 "위반할 가능성이 합리적으로 높다"고 판단하면 접근을 제거하거나 정지할 수 있다. AUP는 완전한 목록이 아니며 게시만으로 언제든 바뀐다.
  2. AUP 1.2: "upload, process, store, or attempt to create any illegal content". 금지 콘텐츠 유형을 제외한 현재 방침을 유지해야 하는 근거이다.
  3. MCA 2.3(l)과 6절: AUP 위반은 MCA 위반이며, 즉시 정지할 수 있고 사전 통지는 "가능한 경우"에만 한다.
  4. MCA 12.3(B): 2.3, 2.4, 5절 위반은 책임 상한의 예외이다. 상한은 최근 12개월 지불액과 50달러 중 큰 금액이다. 현실적 가능성은 낮지만 한도가 없다.
  5. MCA 4.1, 4.3: 입력은 영구적으로 텔레메트리 생성과 부정 사용 감시(fraud and abuse monitoring)에 쓰인다. 모델 학습에는 동의 없이 쓰지 않는다. 공격 문장이 감시에 걸려 정지로 이어질 수 있는 경로이다.
  6. MCA 2.3(g): 접근 제한이나 보호 장치에 대한 보안 시험을 금지한다. 6단계에서 Jev가 속는 비율을 재는 일(R6)은 해석 여지가 조금 있다.
  7. 연구, 레드팀, 분류기 평가 예외는 AUP와 MCA 어디에도 없다. 비상업 학습용이라는 사실은 약관상 효력이 없다.
- 판단: 판정만 하고 내용을 생성하지 않으며 금지 콘텐츠를 제외했으므로 위반 가능성은 낮다. 정지 가능성은 0이 아니다. 정지되면 판정이 실패하고 결정 3에 따라 모든 요청이 차단된다.
- 최초 공식 문서 확인 결과: AUP는 안전 필터 우회와 "TypeSafe의 AI 모델이 TypeSafe 정책에 반하게 동작하도록 의도적으로 유도하는 것"을 금지한다(3.4). 목록은 완전하지 않다고 명시하며, 위반했거나 위반할 가능성이 있다고 판단하면 접근을 제거하거나 정지할 수 있다. 연구, 레드팀, 분류기 평가 목적의 예외 조항과 예외 신청 절차는 문서에 없다.
- 영향: 이 프로젝트는 무기, 생물무기, 인신매매 등을 포함한 공격 문장을 판정 대상으로 전송한다. Jev는 판정만 하고 해당 내용을 생성하지 않으므로 금지 대상이 아닐 수 있으나, 약관만으로는 단정할 수 없다. 정지되면 판정 호출이 실패하고 실패 시 차단 정책(결정 3)에 따라 모든 요청이 차단된다.
- 완화 방안: (1) 공급사 사전 확인은 불가능하다(2026-10-28 답장). (2) `disallowed_content` 유형과 영어 hard negative는 외부로 보내지 않는다(적용 중). (3) `Judge` 인터페이스를 유지하여 다른 모델로 교체할 수 있게 한다(적용 중).
- 추가 완화 (2026-10-28 결정): (4) 6단계 측정 전에 AUP와 MCA를 다시 읽고 수정일을 비교한다. (5) Jev 출력을 모델 학습이나 모방에 쓰지 않는다(MCA 2.3(b)). (6) 무료 크레딧을 얻으려고 계정을 여러 개 만들지 않는다(MCA 8.2(b)). (7) 정지에 대비해 6단계 측정 결과와 판정 로그를 저장소 밖으로 잃지 않도록 커밋한다.

- 확인 시점: 스텝 2.5 (PoC 데이터 범위 결정 전), 6단계 전

## R9. 크레딧 잔액 소진으로 인한 판정 중단

- 상태: 열림
- 공식 문서 확인 결과(MCA): 서비스 이용에는 크레딧이 필요하며 입력마다 소비된다. 구매 크레딧은 환불, 양도가 불가능하고 12개월 후 만료된다. 잔액이 0이 되면 자동 충전을 선택하지 않은 경우 출력 생성을 거절할 수 있다.
- 영향: 잔액이 소진되면 판정이 실패하고 실패 시 차단 정책에 따라 정상 요청도 차단된다. 6단계 배치 측정 중 소진되면 결과가 왜곡된다.
- 완화 방안(제안): 측정 전에 잔액을 확인하고, 판정 실패로 차단된 건을 별도 집계하며, 오류 유형별로 구분해서 기록한다. 단가가 낮아 560건 전체 비용은 1센트 안팎으로 추정한다.
- 확인 시점: 6단계 전

## R10. 시험 문장이 단일 생성기(Gemini)에서 나온 문제

- 상태: 열림
- 배경: 룰 후보 파일과 시험 문장(정상, 경계, 금지, 결합)은 Gemini로 만들었다(모델과 버전은 미상). 스트레스 문장 16개와 보강 문장 22개는 이 대화에서 AI가 작성했다. 응답용 모델도 Gemini 계열이다.
- 영향: 문장의 어휘와 문형이 한 생성기의 습관을 따라 비슷해질 수 있다. 문체 단서(shortcut)나 템플릿 반복이 있으면 측정 수치가 실제 사용자 입력에서의 성능보다 좋게 나온다.
- 완화 방안(제안): (1) 모든 문장에 출처(`source`)와 사용자 검수 여부를 기록한다. (2) 사용자가 직접 쓴 문장을 일정 비율 이상 섞는다. (3) 문체와 길이를 다양하게 만든다(반말, 존댓말, 오탈자, 짧은 문장, 맥락이 긴 문장). (4) 6단계 분석에서 한계로 명시한다.
- 실제 영향 확인 (2026-10-26): 정상 풀 129문장에서 오탐이 0건이던 패턴이 UI 라벨과 오류 문구를 인용하는 현실적 정상 질문에서는 막혔다(대괄호 모드 선언 패턴: 14개 중 12개). 풀에 이런 사용 형태가 없어서 오탐이 가려졌다. 판정 모델 시험에도 같은 한계가 적용될 수 있으므로, 정상 풀 보강 시 UI 인용, 오류 문구, 오탈자, 긴 맥락 같은 현실적 형태를 포함한다.
- 확인 시점: 스텝 2.9-3 (정상 풀 확대), 6단계

## R11. 응답 모델(Gemini 무료 티어)의 데이터 사용

- 상태: 열림 (포트폴리오 단계에서는 수용 가능, 확장 시 재검토)
- 공식 문서 확인 결과 (2026-10-26, Gemini API 추가 이용약관): 무료 티어(Unpaid Services)는 제출한 콘텐츠와 생성된 응답을 제품과 머신러닝 기술의 제공, 개선, 개발에 사용하고, 사람이 입력과 출력을 읽고 처리할 수 있다. 약관은 무료 티어에 민감하거나 기밀이거나 개인적인 정보를 제출하지 말라고 경고한다. 유료 티어는 프롬프트와 응답을 제품 개선에 쓰지 않는다고 명시하되, 금지 사용 정책 위반 탐지를 위해 제한된 기간 기록한다. 유료 데이터의 보관 기간과 사람 검토 여부는 문서에 없다.
- 영향: 사내 HR 문의에는 민감한 정보가 들어갈 수 있다. 실제 직원 질문을 받는 서비스라면 무료 티어를 쓸 수 없다. 이 프로젝트는 시험 문장만 보내므로 지금은 수용 가능하다.
- 완화 방안(제안): 시험과 시연에는 실제 개인정보나 사내 정보를 입력하지 않는다는 규칙을 명세서에 적고, 실제 서비스로 확장하면 유료 티어 전환을 전제 조건으로 기록한다.
- 확인 시점: 스텝 3 (명세서), 스텝 5 (설계서)
